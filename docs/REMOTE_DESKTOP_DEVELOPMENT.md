# 基于 1cat Tunnel 框架实现远程控制桌面的可行性评估与开发方案

## 1. 文档目的

本文档用于评估：在现有 `1cat-tunnel-2` 反向访问框架之上，如何扩展出“远程控制桌面”能力，并给出可落地的开发路线。

这里的“远程控制桌面”分成三类能力：

1. 通过现有隧道直接转发 `RDP` / `VNC`，使用系统自带或第三方桌面客户端连接。
2. 在服务端网页控制台里直接打开浏览器远程桌面。
3. 自研跨平台桌面控制 agent，实现屏幕采集、输入注入、剪贴板、文件传输等完整能力。

本文会明确说明：

- 哪些能力当前框架已经基本具备。
- 哪些能力可以在较小改造下落地。
- 哪些能力会明显增加依赖、复杂度和运维成本。

## 2. 当前框架现状

现有项目本质上已经是一个“控制信令 + 独立数据通道”的 TCP 反向隧道框架：

1. 客户端通过控制连接向服务端注册节点和 `preset`。
2. 服务端为每个 `preset` 自动分配一个公网端口并开始监听。
3. 外部用户访问该公网端口时，服务端向目标客户端发送 `open_connection`。
4. 客户端连接本地目标端口，再额外回连服务端发送 `attach`。
5. 服务端将公网连接和客户端回连的数据连接绑定起来，双向转发字节流。

这套模型对“基于 TCP 的桌面协议”非常友好，因为：

- `RDP` 是 TCP 协议，可直接复用。
- `VNC/RFB` 常见实现也是 TCP，可直接复用。
- 当前服务端已经能统计连接数、活跃会话、入口/出口流量和最近错误。
- 当前客户端已经内置 `RDP` / `SSH` 首启预设，Windows 默认就面向远程桌面场景。

同时也要看到当前框架的边界：

- 只支持 `TCP`，不支持 `UDP`。
- 没有内建 `TLS`。
- 当前仍是共享 token 模式，不是每节点独立凭据。
- 映射和会话状态都在内存中，服务端重启不会恢复。
- 没有操作审计、会话审批、权限模型。
- 当前网页控制台是管理页，不是会话级远程桌面页。

结论很直接：

- “原生 RDP/VNC 桌面访问”已经具备实现基础。
- “浏览器内桌面控制”可以做，但要分协议路线。
- “完全自研桌面控制 agent”不建议作为第一阶段目标。

## 3. 可行性总览

| 路线 | 当前可用度 | 新增依赖 | 跨平台难度 | 是否推荐 |
| --- | --- | --- | --- | --- |
| 直接转发 Windows `RDP` | 高 | 低 | 低 | 强烈推荐，优先落地 |
| 直接转发 Linux `xrdp` | 中高 | 需要客户机启用 `xrdp` | 中 | 推荐 |
| 直接转发 Linux / Windows `VNC` | 中 | 目标机需要 `VNC Server` | 中 | 推荐，适合作为浏览器方案前置 |
| 浏览器内 `VNC` 桌面 | 中 | 需要引入前端静态资源和 WebSocket 桥接 | 中 | 推荐，适合第二阶段 |
| 浏览器内 `RDP` 桌面 | 低到中 | 基本需要额外协议网关或第三方组件 | 高 | 谨慎，建议后置 |
| 自研桌面采集 + 输入注入 agent | 低 | 很高，且有大量系统 API 依赖 | 很高 | 当前不推荐 |

## 4. 推荐结论

如果目标是“尽量少依赖、方便分发、尽快可用”，建议采用下面的路线：

1. 第一阶段：正式化“原生桌面转发”
   - Windows 继续走 `RDP -> 127.0.0.1:3389`
   - Linux 增加 `xrdp` 或 `VNC` 预设
   - 控制台强化桌面节点展示、命令提示、审计记录

2. 第二阶段：实现“浏览器 VNC 桌面”
   - 在服务端网页控制台里新增桌面页面
   - 通过 WebSocket 把浏览器和隧道后的 `VNC` 连接桥接起来
   - 前端嵌入 `noVNC` 类静态资源

3. 第三阶段：评估“浏览器 RDP 桌面”
   - 如果必须在浏览器里控制 Windows 桌面，再考虑引入额外 RDP 网关
   - 不建议直接从当前代码库里自研 RDP 渲染协议栈

一句话总结：

短期最好做“RDP/VNC 直连增强版”，中期最好做“浏览器 VNC”，长期再评估“浏览器 RDP”。

## 5. 路线一：原生 RDP / VNC 直连

### 5.1 可行性

这是当前框架最容易落地的一条路，因为项目已经支持任意 TCP 端口反向暴露。

对于 Windows：

- 默认预设已经是 `rdp -> 127.0.0.1:3389`
- 只要客户机器已开启 Remote Desktop，公网端口映射后即可直接用 `mstsc` 连接

对于 Linux：

- 如果客户机运行 `xrdp`，也可以映射 `127.0.0.1:3389`
- 如果客户机运行 `VNC Server`，则可以映射 `127.0.0.1:5900` 或其他 VNC 端口

### 5.2 这一阶段建议补的能力

#### 服务端

- 在 `preset` 层增加协议类型标识，例如 `ssh`、`rdp`、`vnc`、`tcp-app`
- 控制台将桌面类预设单独归类显示
- 为桌面会话增加“最近访问人、来源 IP、开始时间、结束时间、时长”审计字段
- 增加“复制连接命令”和“复制地址”按钮
- 增加“强制断开当前桌面会话”能力

#### 客户端

- Windows 启动向导保留 `RDP` 作为默认推荐
- Linux 启动向导增加 `XRDP` / `VNC` 选项，而不只给 `SSH`
- 客户端注册前，先检查本地目标端口是否可连接，提前提示“本地 RDP/VNC 服务未启动”
- 将桌面类预设的探测结果上报给服务端，减少“端口分配了但本地服务没开”的误判

### 5.3 这条路的优点

- 对现有架构改动最小。
- 基本不改变当前打包方式。
- Windows 远程桌面体验最好，图像、剪贴板、分辨率适配都由成熟协议负责。
- 服务端仍然保持“纯隧道 + 控制台”的职责，不需要立刻变成复杂的桌面网关。

### 5.4 这条路的局限

- 用户必须本地安装桌面客户端，不能直接在浏览器里打开。
- Linux 桌面前提是客户现场已经安装并配置好 `xrdp` 或 `VNC Server`。
- 目前项目还没有审批、审计、录像、细粒度权限，不适合直接开放给多角色运维团队。

## 6. 路线二：浏览器内 VNC 桌面

### 6.1 为什么先选 VNC，而不是先选 RDP

浏览器天然不直接支持 `RDP`，但浏览器和 `VNC` 的组合更成熟。

常见做法是：

1. 浏览器加载一个 `VNC` 前端页面。
2. 浏览器通过 `WebSocket` 连接服务端。
3. 服务端把 `WebSocket` 二进制流桥接到目标 `VNC` TCP 连接。
4. 目标 `VNC` TCP 连接仍然通过现有 `1cat` 隧道框架建立。

这意味着：

- 现有隧道层基本不用推翻。
- 主要新增的是服务端 HTTP/WebSocket 桥接和一个前端静态页面。
- 只要客户机器上存在 `VNC Server`，浏览器桌面就能工作。

### 6.2 推荐架构

建议新增一个“桌面网关层”，但仍内嵌在当前 `tunnel-server` 里：

1. 控制台新增 `/desktop/:node/:preset` 页面。
2. 页面完成登录校验后，向服务端申请一个一次性桌面会话 token。
3. 浏览器使用该 token 连接 `/ws/desktop/:session_id`。
4. 服务端在后台复用现有 `open_connection -> attach -> TCP proxy` 机制，拿到目标 `VNC` 连接。
5. 服务端将 `WebSocket` 与该 `VNC` 连接桥接。

### 6.3 推荐的代码改造点

#### 协议与模型

- 为 `preset` 增加 `protocol` 或 `category` 字段
- 标记哪些 `preset` 允许网页桌面打开
- 引入桌面会话记录结构，例如：
  - `session_id`
  - `node_name`
  - `preset_name`
  - `created_by`
  - `source_ip`
  - `started_at`
  - `ended_at`
  - `bytes_in`
  - `bytes_out`

#### 服务端

- 增加桌面会话创建接口
- 增加 WebSocket 端点
- 增加会话超时和空闲断开
- 将会话记录展示到控制台
- 在现有 dashboard 的节点卡片中增加“打开桌面”按钮

#### 前端

- 内嵌一个浏览器 `VNC` 客户端页面
- 支持全屏、缩放、断线提示、剪贴板开关
- 与现有登录态复用，避免另做一套认证

### 6.4 依赖影响

这条路通常需要：

- 一个轻量 WebSocket 库
- 一套浏览器 `VNC` 前端静态资源

但它仍然可以保持“服务端单目录分发”：

- 静态资源可以直接打包进 Go 二进制
- 不需要单独安装数据库也能先跑通
- 不需要引入额外系统级 daemon

这与当前项目“少依赖、方便分发”的目标是相容的。

### 6.5 主要风险

- Windows 默认没有 `VNC Server`，如果你不想在客户机额外安装组件，那么这条路对 Windows 不够友好。
- Linux 如果是 Wayland，会遇到屏幕共享权限和输入注入限制，不同桌面环境差异较大。
- 浏览器 VNC 的体验通常不如原生 RDP，特别是在高分辨率和弱网下。

## 7. 路线三：浏览器内 RDP 桌面

### 7.1 可行，但不适合当前阶段优先做

如果你希望“浏览器直接打开 Windows 桌面”，最自然的目标协议其实是 `RDP`，因为 Windows 自带远程桌面服务。

问题在于：

- 浏览器不能直接原生说 `RDP`
- 你需要一个协议转换层，把浏览器侧的交互协议翻译成 `RDP`
- 这通常意味着额外网关组件，而不是简单的 TCP 透传

### 7.2 现实可行的两种做法

#### 做法 A：引入现成 RDP 网关

优点：

- 开发周期短很多
- 能较快得到浏览器访问 Windows 桌面的能力

缺点：

- 基本会新增额外依赖和单独组件
- 与当前“尽量打包成少文件、少依赖”的目标存在冲突
- 维护复杂度明显提升

#### 做法 B：自研浏览器 RDP 网关

优点：

- 理论上可以做到完全内聚在当前产品中

缺点：

- 协议复杂度高
- 图形、输入、音频、剪贴板、重连、多显示器等都要自己处理
- 对当前项目体量来说风险过大

### 7.3 结论

如果一定要做浏览器版 Windows 远程桌面，建议放到第三阶段，并接受“新增网关依赖”的现实；不建议把它当作下一步立即实现的主线。

## 8. 路线四：自研桌面控制 agent

### 8.1 这条路为什么诱人

从产品形态上看，自研 agent 可以做到：

- 不依赖客户机已有 `RDP` 或 `VNC`
- 浏览器直接打开桌面
- 可以统一剪贴板、文件传输、操作授权、屏幕水印
- Windows / Linux 体验可以尽量统一

### 8.2 这条路为什么代价很高

你需要自己完成以下能力：

- 屏幕捕获
- 视频或图像编码
- 鼠标键盘输入注入
- 剪贴板同步
- 文件传输
- 断线重连
- 多显示器支持
- 权限提升与安全确认

而且跨平台会遇到明显系统差异：

- Windows 有 `Session 0` 隔离，服务进程不等于交互桌面
- Linux 在 `X11` 和 `Wayland` 下的桌面控制方式差异很大
- 如果要保持当前项目的静态单文件分发，很容易被原生库、驱动、编码器依赖打破

### 8.3 结论

除非你要做的是“完整商用远控产品”，否则不建议在当前项目阶段走自研 agent 路线。

## 9. 为什么不建议现在直接走 WebRTC 自研桌面

`WebRTC` 适合浏览器端实时音视频和低延迟交互，但它解决的是“媒体传输”问题，不是“桌面采集与控制”问题。

如果没有自研桌面 agent，单纯引入 `WebRTC` 也不能直接得到远程桌面。

对于当前项目：

- NAT 穿透问题已经被“客户端主动回连 + 服务端中转”解决了
- 真正缺的是桌面协议或桌面采集层
- 贸然上 `WebRTC` 会引入更多复杂度，而不会显著缩短第一版落地时间

因此：

- 原生 RDP/VNC 不需要先引入 `WebRTC`
- 浏览器 VNC 也不需要先引入 `WebRTC`
- 只有当你未来决定做自研桌面 agent 时，`WebRTC` 才值得重新评估

## 10. 为远程桌面落地必须补齐的安全能力

远程桌面比普通端口映射风险更高，因为它本质上是“获得客户主机的可视化交互控制权”。在真正进入生产前，至少要补齐下面这些能力：

1. 每节点独立 token，而不是全局共享 token
2. 控制台放到 `HTTPS` 之后，或直接内建 `TLS`
3. 会话审计
   - 谁发起
   - 从哪个 IP 发起
   - 连接到哪个节点和哪个桌面协议
   - 持续多久
   - 是否主动断开
4. 桌面会话审批
   - 可选要求客户侧确认
   - 或要求二次授权
5. 细粒度权限
   - 是否允许文件传输
   - 是否允许剪贴板
   - 是否允许全控制，只读观看，或仅查看日志
6. 端口与会话持久化
7. 失败重试和告警
8. 管理员密码轮换和登录保护

额外要注意：

当前 `bootstrap token` 是“便于交付的加密封装”，不是完整零信任方案；如果未来桌面控制变成核心能力，接入凭据体系要单独升级。

## 11. 建议的开发里程碑

### 11.1 里程碑 M1：原生桌面直连增强

目标：

- Windows 节点稳定提供 `RDP`
- Linux 节点支持 `XRDP` 或 `VNC`
- 控制台对桌面节点有专门展示和审计

建议任务：

1. 为 `preset` 增加协议分类
2. Linux 首启向导增加 `XRDP` / `VNC` 选项
3. 客户端增加本地端口可达性检查
4. 服务端增加桌面会话日志
5. 控制台增加“复制 RDP/VNC 地址”和“断开会话”

验收标准：

- Windows 节点能稳定通过服务端公网地址打开 `RDP`
- Linux 节点能稳定通过 `xrdp` 或 `VNC` 打开桌面
- 控制台能看到桌面会话开始、结束、来源 IP、流量

### 11.2 里程碑 M2：浏览器 VNC

目标：

- 在控制台里直接打开浏览器桌面
- 支持至少 Linux 图形桌面，或已安装 VNC 的 Windows 节点

建议任务：

1. 增加桌面会话创建接口
2. 增加 WebSocket 桥接
3. 内嵌浏览器 `VNC` 页面
4. 增加一次性桌面会话 token
5. 增加空闲超时和手动断开

验收标准：

- 登录控制台后可直接打开某节点桌面
- 断网和客户端离线时能明确提示
- 会话结束后控制台能看到审计记录

### 11.3 里程碑 M3：持久化与权限治理

目标：

- 让桌面能力从“能用”变成“可控、可审计、可恢复”

建议任务：

1. 引入轻量持久化
2. 增加 RBAC 或最少的角色区分
3. 增加每节点独立凭据
4. 增加操作日志与检索
5. 增加桌面会话审批开关

### 11.4 里程碑 M4：可选浏览器 RDP

目标：

- 在接受新增网关依赖的前提下，提供浏览器访问 Windows 桌面的能力

建议任务：

1. 选择 RDP 网关实现路线
2. 设计和当前控制台的登录态集成
3. 调整打包与部署文档
4. 做性能和稳定性压测

## 12. 实施建议

如果你下一步就要继续开发，最稳的起手顺序是：

1. 先把“原生桌面直连”做完整
2. 再做“浏览器 VNC”
3. 把“浏览器 RDP”放成可选高级能力

不要反过来上来就做自研桌面 agent，因为那会快速把项目从“轻量隧道工具”变成“跨平台远控产品”，复杂度会跳一个量级。

## 13. 最终建议

基于当前 `1cat-tunnel-2` 架构，实现远程控制桌面是完全有可能的，但应按下面的优先级推进：

1. 立即可落地：继续强化现有 `RDP` / `xrdp` / `VNC` 透传能力
2. 最值得做的下一步：浏览器内 `VNC` 桌面
3. 不建议立刻做：浏览器内 `RDP` 自研协议栈
4. 当前不建议做：自研跨平台桌面控制 agent

如果目标是“单服务器、少依赖、方便给客户分发”，那么最符合这个目标的组合是：

- Windows：优先 `RDP`
- Linux：优先 `xrdp`，其次 `VNC`
- Web 控制台：第二阶段增加 `VNC` 浏览器入口

这条路线既复用当前框架，也不会过早把系统拖进高复杂度依赖泥潭。
